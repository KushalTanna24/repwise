# PART 3 — PRODUCT VISION

Repwise should become a personalized workout companion that knows my training split, remembers my past performance, creates a balanced next workout, lets me log exactly what I did, and uses that history to recommend sensible progression.

The experience should feel like a coherent fitness application, not a collection of disconnected forms.

The application must support this complete loop:

1. Configure a training profile and select a split.
2. Save that split persistently.
3. Start a workout.
4. Automatically receive the correct next session for the selected split.
5. See exercises, set targets, rep ranges, suggested loads, rest guidance, and previous performance.
6. Modify exercises and targets when needed.
7. Log actual sets, repetitions, weights, and completion status.
8. Finish and save the workout.
9. Update workout history, exercise progress, and relevant metrics.
10. Use the actual results to calculate appropriate future targets.
11. Automatically propose the next workout in the split rotation.
12. Preserve all the data across refreshes, sign-ins, devices where synchronization is supported, and application updates.

The application should support conventional strength training, hypertrophy, general fitness, and bodyweight or calisthenics-oriented training.

It should also retain existing body metrics and progress tracking. Workout planning must not become the entire product at the expense of the rest of the application.

# PART 5 — PERSISTENT SPLIT AND WORKOUT ROTATION

This is one of the most important requirements.

## 5.1 The split is selected once

I should be able to choose a split such as:
- Full Body.
- Upper / Lower.
- Push / Pull / Legs.
- A suitable custom split, if supported.

Once selected, it must remain active across:
- Page refreshes.
- Browser restarts.
- Sign-in and sign-out where appropriate.
- Normal application updates.
- Workout completion.
- Navigation between screens.

It must only change when I intentionally change it.

Do not reselect the split automatically based on a random value, page load, or workout completion.

Do not conflate a training split with a particular workout. The split defines the structure; the workout is the next session within that structure.

## 5.2 Split-specific rotation

Represent each split as an ordered sequence of sessions.

Examples:

Full Body:
- Full Body A.
- Full Body B.
- Full Body C.

Push / Pull / Legs:
- Push.
- Pull.
- Legs.

Upper / Lower:
- Upper.
- Lower.

The exact supported session structure should be established from the existing implementation and user profile.

Persist the current rotation position and enough information to determine the next session reliably.

After a workout is successfully completed, advance the rotation exactly once.

For example:

- Current session: Full Body A.
- Complete the workout.
- Next proposed session: Full Body B.
- Complete that workout.
- Next proposed session: Full Body C.
- Complete that workout.
- Next proposed session: Full Body A in the next cycle.

If the workout is abandoned or merely viewed, do not advance the rotation.

Refreshing the page must not advance the rotation.

Opening workout history must not advance the rotation.

Double-clicking Finish must not advance the rotation twice.

## 5.3 Dynamic but balanced workout combinations

Workout combinations should have meaningful variation.

For a Full Body split, A, B, and C should not simply be identical lists with different names.

They should vary emphasis, movement selection, and accessory exercises while remaining balanced across the training cycle.

For example, across the full-body rotation, account for:
- Knee-dominant lower-body movement.
- Hip-dominant movement.
- Horizontal push.
- Vertical push where appropriate.
- Horizontal pull.
- Vertical pull.
- Core work.
- Optional unilateral work.
- Optional calves, arms, shoulders, or other accessories according to the user's goals and time.

Not every category needs to appear in every session, but the overall rotation must provide balanced coverage.

Avoid unnecessary duplication of the same high-fatigue movements across consecutive sessions.

Use the user's available equipment and exercise preferences.

Keep important compound movements sufficiently consistent to measure progress. Rotate accessories more freely.

Variation must not destroy comparability. If an exercise is replaced with a substantially different movement, do not present its performance history as though the movements were identical.

## 5.4 Deterministic and explainable planning

Workout generation must be reproducible.

Given the same:
- User profile.
- Split.
- Rotation state.
- Exercise catalogue.
- Recent training history.
- Equipment.
- Constraints.

The planner should produce a consistent valid plan unless an explicit variation rule calls for a different cycle.

Do not generate an entirely new workout every time the page loads.

Persist the proposed workout when appropriate so that refreshing the page does not unexpectedly change exercises or targets.

A new rotation cycle can use controlled variation, but the variation should be explainable and balanced.

If no suitable exercise is available, explain the problem and offer a valid alternative rather than silently producing an incomplete workout.

# PART 6 — PROGRESSIVE OVERLOAD USING ACTUAL RESULTS

This is another core requirement.

The app must not merely generate fixed workouts. It must use the user's actual completed sets, repetitions, and weights to recommend sensible future targets.

## 6.1 Store targets and results separately

For every planned set, distinguish between:
- Target repetitions or repetition range.
- Target weight.
- Actual repetitions.
- Actual weight.
- Completion status.
- Whether the set was skipped.
- Any relevant notes.

Never overwrite actual results with recommended targets.

Preserve the date, exercise identity, workout identity, and session identity needed to reconstruct performance history.

## 6.2 Double progression

Use a clear, configurable double-progression strategy for suitable weighted exercises.

Example:

An exercise is prescribed for 3 sets of 8–12 reps at 20 kg.

Session 1:
- Set 1: 10 reps at 20 kg.
- Set 2: 9 reps at 20 kg.
- Set 3: 8 reps at 20 kg.

The user has not yet reached the top of the target range for all prescribed sets. A reasonable next target may be to keep the weight at 20 kg and gradually improve repetitions.

Later session:
- Set 1: 12 reps at 20 kg.
- Set 2: 12 reps at 20 kg.
- Set 3: 12 reps at 20 kg.

If all required sets were completed with good performance, the next session can recommend a small load increase and return to the lower or middle portion of the repetition range.

The application should not demand an arbitrary percentage increase regardless of the exercise or available equipment.

## 6.3 Weight increments

Load progression should depend on:
- Exercise type.
- Available equipment increments.
- Current load.
- The user's actual performance.
- The target repetition range.
- Whether the prescribed sets were completed.

Use small, practical increments where appropriate.

For example, dumbbells and barbells may have different available increments. Do not assume every exercise can increase by the same number of kilograms.

If the available equipment does not support the suggested increment, keep the current load or provide a practical alternative.

## 6.4 Performance drops

If the user struggles or performs fewer repetitions than expected:
- Do not automatically increase the load.
- Consider maintaining the load and target.
- Suggest a small reduction if repeated performance indicates the current target is too demanding.
- Consider fatigue, missed sessions, or an unusually poor session before making aggressive changes.
- Do not punish a single bad session by resetting all progress.
- Avoid treating incomplete workouts as successful completion.

Recommendations should be conservative, understandable, and reversible.

## 6.5 Progression must be based on completed work

Do not calculate successful progression from:
- Planned sets that were never performed.
- Default values that the user never confirmed.
- Skipped sets.
- Abandoned workouts.
- Incomplete records incorrectly treated as completed sets.

Where actual results are missing, say that there is insufficient information to adapt the recommendation.

## 6.6 Bodyweight and calisthenics progression

Not all exercises use an external load.

For pull-ups, dips, push-ups, and similar movements, consider:
- Completed repetitions.
- Set quality as recorded by the user.
- Assistance level.
- Added weight.
- Range of motion or tempo where explicitly tracked.
- Appropriate movement variations.
- Progression from assisted to unassisted variations when the data supports it.

Do not invent a user's bodyweight or infer assistance levels that were never recorded.

If a movement changes significantly, keep the new variation's history distinguishable from the old variation.

## 6.7 Previous performance and explanations

Each suggested target should have a short explanation.

Examples:
- "Keeping the same weight because you completed 9, 8, and 8 reps last time."
- "Increasing the load slightly because you completed all prescribed sets at the top of the repetition range."
- "Holding the target steady because the previous session was incomplete."
- "No progression recommendation yet because there is no completed history for this exercise."

These explanations must reflect actual application data, not generic messages unrelated to performance.

## 6.8 Avoid fake intelligence

Implement a deterministic progression engine with explicit rules, test cases, and explainable decisions.

An external AI model is not required for the initial implementation.

If an AI feature is later proposed, make it optional and do not let it bypass data validation, progression limits, or user control.

Preserve the existing JSON export and restore features if present.

Export should include the data necessary to reconstruct the user's supported application state.

Import should:
- Validate the file format and schema.
- Detect unsupported versions.
- Show the user what will be imported or replaced.
- Prevent accidental deletion of current data.
- Back up existing data before a destructive restore.
- Avoid duplicate records where possible.
- Fail safely when data is invalid.

Do not claim a backup exists unless the backup was actually created and verified.

# PART 11 — ACCEPTANCE TESTS

These are required behavioral outcomes, not merely ideas.

## Split persistence
1. Select Full Body.
2. Refresh the application.
3. Confirm Full Body remains selected.
4. Navigate to another screen and return.
5. Confirm the split remains unchanged.

## Correct rotation
1. Start Full Body A.
2. Finish it successfully.
3. Confirm the next session is Full Body B.
4. Finish B.
5. Confirm the next session is Full Body C.
6. Finish C.
7. Confirm the next session begins the next rotation cycle correctly.

Refreshing, opening history, or viewing a session must not advance the rotation.

## Dynamic but balanced sessions
Verify that Full Body A/B/C provide meaningful variation and balanced movement coverage without producing three identical workouts.

Verify that variation does not make exercise histories misleading.

## Actual performance and progression
1. Log real sets, repetitions, and weights.
2. Finish the workout.
3. Open history.
4. Confirm actual values are saved.
5. Start the next relevant session.
6. Confirm targets use the recorded performance.
7. Confirm the suggested load and repetitions follow the progression rules.
8. Confirm the application explains why the recommendation changed.

## Incomplete workouts
Verify that skipped and unfinished sets do not count as successfully completed work.

Verify that an abandoned workout does not advance the split automatically.

## Body metrics
1. Enter height.
2. Record body weight on a date.
3. Verify BMI calculation.
4. Add more dated weight entries.
5. Verify history and charts.
6. Refresh the application.
7. Confirm the records remain available.

## Authentication and data
Verify that:
- A signed-in user can access their own data.
- One user cannot access another user's records.
- Synchronization errors do not silently erase local data.
- Export produces a valid file.
- Import validates data before modifying the existing state.
- Existing records survive a safe migration.

## Regression protection
Verify that adding workout progression has not removed:
- Login.
- Settings.
- Goals.
- Workout history.
- Body-weight history.
- BMI.
- Strength and repetition charts.
- Export and restore.
- Cloud synchronization.

A new feature is not complete if it causes an unrelated existing feature to disappear or break.
